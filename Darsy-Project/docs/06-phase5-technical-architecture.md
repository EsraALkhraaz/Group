## 1. اختيار التقنيات

| الطبقة | الاختيار | السبب |
|---|---|---|
| **اللغة** | TypeScript | الفريق يكتب React بالفعل؛ لغة واحدة تعني وحدة مالية واحدة مشتركة بين الطرفين |
| **إطار الخادم** | **Fastify** | خفيف، تحقق من المدخلات مدمج عبر JSON Schema، أسرع من Express بلا تعقيد Nest |
| **قاعدة البيانات** | PostgreSQL 14+ | القيود والفهارس الجزئية والمشغّلات في `05` تعتمد عليه |
| **الوصول للبيانات** | **Drizzle** أو `pg` مباشرة + **node-pg-migrate** | ⚠️ انظر التحذير أدناه |
| **المهام المجدولة** | **pg-boss** | يعمل داخل PostgreSQL نفسه — لا Redis ولا خدمة إضافية |
| **تخزين الملفات** | S3-compatible (MinIO ذاتيًا أو مزوّد) | الإيصالات والمستندات لا تُخزَّن في قاعدة البيانات ولا في مسار عام |
| **التحقق من المدخلات** | Zod على الحدود | كل ما يدخل من الشبكة غير موثوق حتى يُفحص |

> ⚠️ **تحذير في اختيار ORM:** قيمة مخططنا في **القيود والمشغّلات والفهارس الجزئية**، وهي ما لا تُعبّر عنه معظم الـORMs. ORM يملك المخطط ويولّده سيحذف قيودنا في أول هجرة أو يتجاهلها.
>
> **القاعدة:** **الهجرات تُكتب SQL يدويًا** (node-pg-migrate)، والـORM — إن استُخدم — **للاستعلام فقط لا لتعريف المخطط**.

## 2. تنظيم الطبقات

```
apps/
  api/                    الخادم
    routes/               HTTP فقط: تحقق، صلاحية، استدعاء الخدمة، تحويل الرد
    services/             منطق الأعمال — لا يعرف شيئًا عن HTTP
    repositories/         SQL فقط — لا منطق أعمال
    jobs/                 المهام المجدولة
    providers/            تنفيذ مزوّدي الدفع
  web/                    تطبيق React الحالي
packages/
  money/                  ★ قواعد المال — مشتركة بين الطرفين
  shared-types/           أنواع الطلبات والردود
```

### 2.1 وحدة المال — أهم قرار في هذا المستند

`lib/money.js` الموجود اليوم **يُنقل كما هو** إلى `packages/money` ويُستورد من الطرفين:

- **الخادم** يستعمله ليقرر: هو **المصدر الوحيد للحقيقة** (BR-PAY-2).
- **الواجهة** تستعمله لتعرض فقط: «ستدفع 30، يصل المدرس 25.5» قبل الإرسال.

وهذا يحقق أمرين معًا: **الرقم المعروض هو الرقم المحسوب** (لا اختلاف بين شاشة وخادم)، و**القرار في الخادم وحده** — الواجهة لا تُرسل مبلغًا، ترسل `bookingId` فقط ويحسب الخادم الباقي.

> **قاعدة حاسمة:** لا يقبل الخادم **أي مبلغ** من العميل. يقبل معرّفات فقط، ويشتق كل رقم من قاعدة البيانات وإعداداتها.

## 3. المصادقة والصلاحيات

| البند | القرار |
|---|---|
| كلمة المرور | **argon2id** (أو bcrypt بـ12 جولة). لا عمود نصي أصلًا في المخطط |
| الجلسة | **JWT قصير (15 دقيقة) + Refresh Token دوّار** يُخزَّن في قاعدة البيانات ويمكن إبطاله |
| النقل | HttpOnly + Secure + SameSite cookies — لا `localStorage` للرموز |
| التحقق من الهاتف | OTP من 4 أرقام، صلاحية 5 دقائق، **3 محاولات كحد أقصى**، ومهلة إعادة إرسال 60 ثانية |
| الصلاحيات | `preHandler` في Fastify يتحقق من الدور على **كل** مسار — لا اعتماد على إخفاء الأزرار |
| تحديد المعدل | على الدخول والـOTP خاصة: 5 محاولات لكل رقم في 15 دقيقة |

**مزوّد الرسائل القصيرة قرار مفتوح 🔴:** لم يُحسم بعد. يُعزل خلف واجهة `SmsProvider` بنفس منطق `PaymentProvider`، وفي التطوير يُطبع الرمز في السجل بدل إرساله.

## 4. طبقة مزوّدي الدفع

خمسة مرشحين وسوق متحرك ⟵ التجريد ليس ترفًا:

```ts
export interface PaymentProvider {
  readonly name: string;
  createSession(input: { bookingId: string; amount: number; returnUrl: string }): Promise<{ sessionId: string; redirectUrl?: string; requiresOtp?: boolean }>;
  confirmOtp?(sessionId: string, code: string): Promise<PaymentResult>;   // Sadad و Adfali
  verifyWebhook(rawBody: Buffer, headers: Record<string, string>): WebhookEvent | null;
  refund(paymentRef: string, amount?: number): Promise<RefundResult>;     // amount غائب = استرجاع كامل
  capabilities: { partialRefund: boolean; otp: boolean };
}
```

`capabilities` ليست زينة: إن كان `partialRefund = false` فالتطبيق **يعرف قبل المحاولة** أنه لا يستطيع تنفيذ رسوم الإلغاء عبر البوابة، فيحوّل المبلغ إلى الرصيد بدل أن يفشل أمام المستخدم.

### 4.1 مسار الـWebhook — الأكثر حساسية في النظام

```
استلام ← التحقق من التوقيع ← تسجيل في webhook_events (unique يمنع التكرار)
       ← رد 200 فورًا ← معالجة غير متزامنة عبر pg-boss
```

**الرد بـ200 قبل المعالجة مقصود:** المزوّد لا ينتظرنا، وفشل المعالجة لا يجعله يعيد الإرسال بلا نهاية. المعالجة تُعاد داخليًا عبر المهام.

## 5. المهام المجدولة (pg-boss)

| المهمة | التكرار |
|---|---|
| انتهاء طلبات الحجز | كل 5 دقائق |
| انتهاء جلسات الدفع | كل 5 دقائق |
| تذكير قبل الحصة بـ30 دقيقة | كل 15 دقيقة |
| معالجة Webhooks المعلّقة | مستمر |
| مطابقة كشف المزوّد بالدفتر | يوميًا |
| نسخة احتياطية + اختبار استرجاعها | يوميًا / أسبوعيًا |

> **النسخة الاحتياطية التي لم تُختبر استعادتها ليست نسخة احتياطية.** في نظام يحتفظ بأموال الناس، اختبار الاستعادة شهريًا التزام لا خيار.

## 6. الملفات

الإيصالات ومستندات الهوية (NFR-SEC-4):

- تُخزَّن بمفتاح عشوائي لا باسم الملف الأصلي.
- الوصول عبر **روابط موقّعة قصيرة العمر** (5 دقائق) — لا مسار عام دائم.

- **فحص نوع المحتوى فعليًا** لا بالامتداد.

## 7. الواجهة — ما يتغير وما لا يتغير

**لا يتغير:** الشاشات الست والعشرون، والتوجيه، والتصميم، وبنية الحالة التي تقرأها الشاشات.

**يتغير:** `AppContext` فقط. اليوم يقرأ من `localStorage`، وغدًا من API. لأن كل الشاشات تقرأ عبر `useApp()` ولا تلمس التخزين مباشرة، **فالتبديل يقع في ملف واحد**.

هذا لم يكن صدفة — كان قرارًا منذ اليوم الأول.

```
useApp()  ─┬─ اليوم:  localStorage
           └─ غدًا:   React Query ← REST API
```

**يُضاف:** React Query لإدارة التخزين المؤقت وإعادة الجلب، وحالات التحميل والخطأ في الشاشات، ومعالجة انقطاع الشبكة.

## 8. البيئات والنشر

| البيئة | الغرض |
|---|---|
| `development` | جهاز المطوّر، قاعدة بيانات محلية، OTP يُطبع، دفع وهمي |
| `staging` | نسخة كاملة ببيانات تجريبية وSandbox المزوّد |
| `production` | الحقيقي |

**النشر المقترح:** خادم واحد (VPS) + Docker Compose: `api` و`postgres` و`minio` و`caddy` (HTTPS تلقائي). لا حاجة لـKubernetes في منصة بهذا الحجم — والبساطة هنا ميزة تشغيلية لا نقص.

**القياس لاحقًا:** فصل قاعدة البيانات أولًا عند الحاجة، ثم نسخ متعددة من الـAPI خلف موازن.

| المستوى | ما يُختبر | الأداة |
